# Architecture Review — Quadraplex-T-3000

_Generated: 2026-08-30_

## 1. Overall Architecture

Quadraplex-T-3000 is an Ansible-driven homelab deployer for a single physical host (`inventory/hosts.yml` defines exactly one host, `home`). It installs Docker (`roles/docker`), a Traefik reverse proxy (`roles/traefik`), and then a set of "stacks" (media, utility, dns) whose services are defined declaratively in `vars/stacks/<name>/base.yml` as a dict of `enabled/version/networks/traefik` blocks per service. A generic engine — `roles/dynamic-stack` (picks enabled services, renders each service's `templates/services/<svc>.yml.j2` fragment, and assembles one `docker-compose.yml`) plus `roles/base-stack` (generic directory/config/compose-up/verify mechanics shared by any stack) — turns that declarative data into a running Docker Compose stack. A parallel `roles/backup` role handles Postgres/SQLite/config/data backups with systemd timers and rclone→S3 sync. Everything is invoked through `make` targets that wrap `ansible-playbook`, with vault-encrypted secrets (`vars/stacks/*/vault.yml`, `inventory/group_vars/vault.yml`) kept properly out of git.

The core idea (services-as-data → generic templating engine → generic deploy role) is genuinely good and is the strongest part of the design. The weak part is that this generic idea is applied inconsistently: the proxy stack (`roles/traefik`) and the media/monitoring stacks (`roles/dynamic-stack` + `roles/base-stack`) each reimplement the same directory/config/compose-up/verify lifecycle by hand rather than sharing it, and the Makefile layer has grown three overlapping copies of the same deploy/status/logs/restart CLI.

## 2. What's Well-Designed

- **Data-driven service composition** (`vars/stacks/media/base.yml` → `roles/dynamic-stack/templates/services/*.yml.j2` → generated `docker-compose.yml`): adding a new service is "add a vars entry + one small template," which is a nice, appropriately-scoped abstraction for a homelab that runs 50+ optional containers.
- **Vault handling**: secrets are split per-stack (`vars/stacks/media/vault.yml`, `vars/proxy/vault.yml`, `inventory/group_vars/vault.yml`), all genuinely AES256-encrypted, `.vault_password` is gitignored and not tracked. This is correctly scoped, not over-built.
- **Backup role** (`roles/backup`): separate tasks per concern (postgres, sqlite, config, data, s3-sync, retention, systemd-timers) is reasonable given it actually needs to handle several different data types and a retention/offsite-sync policy.
- **pre-checks role**: small and focused (verify Docker, ensure a venv for Ansible's Python deps) — appropriately minimal.

## 3. Overkill / Unnecessary Complexity

- **Three make front-ends for the same job** — `makefiles/base-stack.mk`, `makefiles/deploy.mk`, `makefiles/proxy.mk` each independently define `deploy`, `status`, `logs`, `restart`, `stop`, `start`, `down`, `pull`, `update`, `validate-stack`, `validate-target`, `require-stack-path`, `list-stacks`, `list-hosts`, `check-syntax`, `init-stack`, `help`, etc. Running `make help` today literally prints GNU Make "overriding recipe" warnings for `list-stacks`, `list-hosts`, `ping`, `facts`, `check-syntax`, `init-stack`, `validate-stack`, `validate-target`, `require-stack-path`, and `help` — confirmed by running `make -n help`. `deploy.mk` (407 lines) is functionally a near-total superset/clone of `base-stack.mk` (320 lines) plus the proxy targets from `proxy.mk` (245 lines), just with `stack-`/`proxy-` prefixes. Only one of the three copies of each target actually wins (whichever `include` line comes last in the root `Makefile`), so two-thirds of this code is silently dead weight that still has to be read and maintained.
- **Environment-tier abstraction (`ENV=production/staging`) for one host and one environment.** `vars/stacks/media/production.yml` and `vars/stacks/utility/production.yml` are 0 bytes; `vars/stacks/dns/production.yml` is just `---`. No `staging.yml` exists anywhere despite `deploy.mk`/README examples referencing `ENV=staging`. The `deploy-stack.yml` playbook even has the environment-overlay `vars_files` line commented out (`# - "../vars/stacks/{{ stack_type }}/{{ environment... }}.yml"`), meaning the ENV concept currently does nothing at all — it's pure unused indirection carried through inventory patterns, Makefile flags, `validate-stack` checks, and `show-config`/`stack-config` targets.
- **`roles/traefik` duplicates `roles/base-stack` almost line-for-line** instead of reusing it. Diffing `roles/traefik/tasks/directories.yml` vs `roles/base-stack/tasks/directories.yml` and `docker-compose.yml` vs `docker-compose.yml` shows the same steps (create dirs, network create, stop/start compose, systemd unit, health check) reimplemented with `proxy_stack`/`proxy_stack_runtime_user` naming instead of the already-generic `stack_config`/`stack_user_id` variables the rest of the repo uses. There's no structural reason the proxy couldn't be just another "stack" run through `dynamic-stack` + `base-stack`.
- **Duplicated/stale template**: `roles/dynamic-stack/templates/configs/prometheus.yml.j2` is a near-copy of `roles/base-stack/templates/configs/prometheus.yml.j2` (diff shows a missing Loki scrape block) but is never actually referenced — `roles/base-stack/tasks/configs.yml` resolves `configs/prometheus.yml.j2` against its own role's template dir, so the `dynamic-stack` copy is dead and already drifting from the real one.
- **Two config layers for essentially the same monitoring stack**: `roles/base-stack/templates/configs/{prometheus,loki,promtail}.yml.j2` (rendered configs) live in a different role from `roles/dynamic-stack/templates/services/{prometheus,loki,promtail,cadvisor,node_exporter}.yml.j2` (compose service fragments) for what is conceptually one "monitoring" concern, split by an internal implementation seam the reader has to already understand to find anything.
- **Empty scaffolding files**: `roles/dynamic-stack/vars/main.yml` and `roles/base-stack/vars/main.yml` are empty `---` files, `roles/base-stack/README.md` and `roles/dynamic-stack/README.md` contain identical placeholder content that doesn't describe either role (it's a generic "media stack overview" write-up with `[will working on this next weekend]` still in it).
- **`makefiles/clamav.mk`** (146 lines) is present but commented out of the root `Makefile` (`#include makefiles/clamav.mk`) — currently unreachable/dead code.
- **Three separate backup docs** (`docs/BACKUP.md` 523 lines, `docs/BACKUP-QUICKSTART.md` 194 lines, `docs/BACKUP-IMPLEMENTATION-SUMMARY.md` 296 lines, >1000 lines total) for one backup role, with substantial content overlap between the "summary" and the main doc.
- **Root-level `inventory.ini`** duplicates/conflicts with `inventory/hosts.yml` (the actual inventory used) and sets a different `ansible_python_interpreter` (`/opt/ansible-venv/bin/python` vs `/usr/bin/python3` in `ansible.cfg`) — looks like an abandoned earlier inventory format left in place.

## 4. Concrete Simplification Suggestions

- **Collapse the three deploy Makefiles into one.** Keep `makefiles/base-stack.mk`'s generic `STACK=`/`TARGET=` targets (deploy/status/logs/restart/pull/update/validate-*), add the handful of proxy-specific lines from `proxy.mk` as thin wrappers (`proxy-deploy: ; $(MAKE) deploy STACK=proxy ...` if proxy is folded into the stacks dir, or just 4-5 proxy targets), and delete `makefiles/deploy.mk` entirely — it adds no behavior `base-stack.mk`/`proxy.mk` don't already provide, just renamed targets.
- **Drop the ENV/staging concept until it's real.** Either delete the empty `production.yml` files and the `ENV` parameter/`validate-stack` env-file checks, or actually wire the commented-out vars_files line back into `playbooks/deploy-stack.yml` and populate a real staging file. Right now it's pure surface area with zero behavior.
- **Fold `roles/traefik` into the `dynamic-stack`/`base-stack` pattern**, or at minimum rename its variables to match (`stack_config`, `stack_user_id`/`stack_group_id`) and delete the duplicated task files, keeping only what's truly Traefik-specific (ACME/Cloudflare cert config).
- **Delete `roles/dynamic-stack/templates/configs/prometheus.yml.j2`** (confirmed dead/stale duplicate of the base-stack copy) and consider moving all monitoring-related config templates (`prometheus`, `loki`, `promtail`) into one role's `templates/` tree so there's a single place to look.
- **Remove `makefiles/clamav.mk` inclusion decision**: either re-enable it in the root `Makefile` or delete the file — a permanently-commented include is a maintenance trap.
- **Delete the stale `inventory.ini`** at repo root; it's superseded by `inventory/hosts.yml` and disagrees with `ansible.cfg` on the Python interpreter path.
- **Merge the three backup docs into one.** A single `docs/BACKUP.md` with a "Quickstart" section at the top would serve the same purpose with far less to keep in sync (this is a homelab; three audiences for one feature is more than needed).
- **Replace the two placeholder `README.md` files** (`roles/base-stack/README.md`, `roles/dynamic-stack/README.md`) with either real one-paragraph descriptions of what each role actually does, or delete them — copy-pasted, unfinished, wrong-topic READMEs are worse than none.
- **Update the top-level `README.md`'s folder structure diagram**, which describes roles/playbooks that no longer exist (`media-stack/`, `utility-stack/`, `secrets-management/`, `site.yml`, `deploy-media-stack.yml`) — it documents an earlier iteration of the repo (visible in the git log around commits `662d084`/`96b2bf6`) and will actively mislead anyone using this as a template, which the README says is its whole purpose for being public.
- **Remove the empty `roles/*/vars/main.yml`** scaffold files unless something is planned for them.

## 5. Structural Inconsistencies

- **`vars/proxy/` vs `vars/stacks/<name>/`**: the proxy config lives in a flat `vars/proxy/{base,vault}.yml` + `vars/proxy/traefik/traefik-routes.yml`, while every other stack follows `vars/stacks/<name>/{base,production,vault}.yml`. Two different conventions for the same kind of data (per-stack config) with no obvious reason proxy is special.
- **Make target namespacing is inconsistent**: `base-stack.mk` uses bare verbs (`deploy`, `status`, `restart`), `deploy.mk` uses prefixed verbs (`stack-deploy`, `proxy-deploy`), and `proxy.mk` uses bare verbs again but scoped to proxy only (`deploy-proxy` as the entry point, then bare `status`/`logs`/`restart` for proxy) — three different naming schemes for the same action across the three files, colliding at include time as shown by the make override warnings.
- **`roles/base-stack` is misleadingly named** — its README describes it as the media/Arr stack itself, but its actual code (`tasks/directories.yml`, `configs.yml`, `docker-compose.yml`, `verify.yml`) is a generic Compose-lifecycle helper invoked by `dynamic-stack` for *any* stack (media, utility, dns). The name and the (stale) README both suggest something narrower than what the code does.
- **Duplicate near-identical READMEs** between `roles/base-stack/README.md` and `roles/dynamic-stack/README.md` (byte-for-byte the same content, describing neither role accurately) — looks like a copy-paste that was never customized.
- **Single-host inventory (`home`) but multi-host abstractions everywhere**: `TARGET=`, `SERIAL=`, `deploy-all`/`stack-deploy-all` "confirm before deploying to ALL hosts in group" prompts, and `list-hosts`/`ansible-inventory --graph` utility targets all assume a fleet, but `inventory/hosts.yml` defines exactly one host. This isn't necessarily wrong for a project marketed as a "template for others," but it's a real source of the "overly complicated" feeling the README itself admits to.
- **`vars/versions.yml` only pins Docker/containerd/compose versions**; all the ~50 service versions live inline in `vars/stacks/media/base.yml`'s `media_stack.versions` map instead, so there are two different places version pinning happens depending on which component you're looking at.
